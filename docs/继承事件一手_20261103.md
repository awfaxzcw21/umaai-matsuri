# 心意的继承事件一手（t31 / t55 上限抬 + 五维送，2026-11-03）

任务 **#37**。要解决的问题：LF 靶子 §2b 说「t31 / t55 各抬一次上限」是 LF 的硬门槛，
但发表会四场表里**没有抬 `max_*` 的通道**（`single_mode_15_check_point_effect` 只有
`{2,4,202,204}` 四类效果）。这条通道到底落在哪、值多少分、能不能接线——本文给一手答案。

一手来源 = `E:/HJM/jidianbeiAI0.22/out/hachimi_raw` 的 msgpack 报文（只读）。
脚本 `tools/cap_trace.py`（逐报文把 `max_*` / `default_max_*` / 五维 做差分，并回溯触发它的
`*_notify_request`），完整读数 `out/_cap_trace_20261103.txt`，差分表 `out/_cap_trace_20261103.csv`。
**没有一个拟合系数**：所有数字都是从报文里读出来或从仓里已有的表（`data/constants.json`
的 `five_status_final_score`）算出来的，可重跑。

样本：报文库里共 13 局（按 `chara_id` + `start_time` 分组）。其中 **10 局的回合范围同时覆盖
面板 t31 和 t55**（168 / 169 / 170 / 171 / 172 / 179 / 201 / 202 / 203 / 204），另外 3 局没覆盖
（173 只到 t9、180 只有 t1、200 只到 t12）⇒ **抬升样本 20 个 = 10 局 × 2 次，不是「10 局里
有几局抬了」**。缺 t31/t55 的局没有反例，别把它们算成「没抬」。

## 1 结论一：落点 = `story_id 400000040`「心意的继承」，每局正好两次

`tools/cap_trace.py` 把 20 个抬升样本回溯到的触发源**完全一致**：

| 字段 | t31 那一次 | t55 那一次 |
|---|---|---|
| `event_id` | 7040 | 7041 |
| `story_id` | **400000040** | **400000040** |
| `chara_id` | **0** | **0** |
| `succession_event_info.effect_type` | 1 | 2 |
| `choice_array` | `[]`（空） | `[]`（空） |
| 10 局覆盖情况 | **10/10 都触发** | **10/10 都触发** |

`chara_id = 0` ⇒ 这是**剧本级**事件，不是角色专属事件。报文里 `event_id` 的编号空间跟
`single_mode_story_data.id` **不是同一个键**：拿 `7040 / 7041` 去查 `single_mode_story_data`
会得到 `story 501072704 / 501072705`、`card_chara_id 1072`，看着像「某个角色的专属事件」——
那是**错连接**，真值只认报文 `unchecked_event_array` 里的 `story_id 400000040`。
（踩过，记在这里免得再踩。用 35 张 `*event*` 表扫 `7040/7041` 也是零命中。）

**没有分支**：20 个样本的 `select_index_info_array` 全是 `{branch_number:1, select_index:1}`
（distinct = 1），`choice_array` 空 ⇒ 玩家在这个事件上**没有选择**，收益方差不可能来自选项。

**与先前记录的关系**（免得当成全新发现）：这条通道 10-31 就被命名过——
`docs/机制对照表_20261031.md:352` 与 `docs/交接_上游合并重活_20261102.md:172` 记作
「**想いの継承**（t31 触发）」，那两条的数正是本文 run179 t31 那一格
（速+31 / 力+58 / 根+33 / 智+58、耐+0；上限 +4/+2/+11/+4），并且当时已写下用户口径
「**每种马给的都不一样，不能当常数建模**」。本文的增量只有四点：
① 它是**每局两次**（t31 + t55，`effect_type` 1 / 2），先前只记了 t31；
② `story_id 400000040` / `chara_id 0` ⇒ 剧本级、非角色专属；
③ 覆盖率 **10/10**（覆盖到那两个回合的局全部触发），不是偶发；
④ 两条腿的**分数估值**（§3）和驱动量排查（§4）。
先前的「不能当常数建模」被本文 §4 独立复现并加强，所以 §5 的裁决与既有口径一致，不是新决策。

## 2 结论二：这条通道**同时送五维**，不是纯上限通道

原来 #37 的框架是「找抬上限的那一步」。找到了，但它不是只抬上限——同一条报文里
五维和 `max_*` **一起动**（20/20 都是如此）：

| 腿 | 20 样本合计 | 单次范围 | 每局（2 次）合计 |
|---|---|---|---|
| 五维送 `ds`（速/耐/力/根/智 之和） | **3,294** | 73–280 | 167–490（均值 329.4） |
| 上限抬 `dm`（`max_*` 之和） | **448** | 11–42 | 23–66（均值 44.8） |

`default_max_*` 差分 `dd` 在 **20/20 全是 0** ⇒ 抬的是**生效上限**，不动**默认上限**。
这条判别很关键：默认上限在全部报文里都是 1200，所以「1200 软上限」和「生效上限被抬」
是两件事，别混。

顺带确认：同一报文里 `fans` 差分 = 0；`nickname_id_array` **20 个样本只有 4 个追加**
（169 t31 `[103,135]` / 170 t31 `[103,135]` / 170 t55 `[107]` / 203 t55 `[103]`，其余 16 个空）
⇒ あだ名 与本事件**不同步**，不是这条通道的固定腿，**本事件不建模它**。

## 3 估值：送分 vs 带宽分（用仓里已有的表，不新造数）

把两条腿都换算成**評価点**，用的是引擎已经在用的同一张表和同一个 `revise`：

```
score(v) = five_status_final_score[revise(v)]        # data/constants.json，len=3802
revise(v) = v            (v ≤ 1200)
          = 2v − 1200     (v > 1200)                 # 已定案的第二段折线
送分  = Σᵢ [ score(現値ᵢ + dsᵢ) − score(現値ᵢ) ]      # 用抬前 現値
带宽分 = Σᵢ [ score(min(上限ᵢ + dmᵢ, 2500)) − score(min(上限ᵢ, 2500)) ]   # 用抬前 上限
```

| 腿 | 10 局合计 | 每局均值 | 每局范围 |
|---|---|---|---|
| **送分**（五维那一下直接值多少） | **16,044** | **1,604** | 577 – 3,235 |
| **带宽分**（上限抬高后多出来的空间值多少） | **7,904** | **790** | 397 – 1,163 |

（这张表 = `python tools/cap_trace.py --value` 的直接输出，不是手算。）

逐局：

```
run168 送 1698 带宽 1163    run172 送 1957 带宽  799    run201 送  815 带宽  397
run169 送 2207 带宽 1048    run179 送 1153 带宽  609    run202 送  577 带宽  553
run170 送 2486 带宽 1163    run203 送  891 带宽  492    run204 送 1025 带宽  801
run171 送 3235 带宽  879
```

**这两条腿的读法必须谨慎，它们不是可以相加的预测值**：
- 送分按「抬前现值」定价 ⇒ 是这一下的**边际下限**（没算这 100 多点之后还能喂给后续训练）；
- 带宽分按「多出来的空间最终会被填满」定价 ⇒ 是上限抬升的**乐观上限**（现值离上限还远的时候，
  抬上来的空间可能一辈子没被用到）；
- 两者都只描述**已观测到的那一格报文**，不能直接拿去和别的通道相加做 LF 预算。
  要相加得先证不重复计入，本仓现在没有这个证明。
- **口径范围**：`tools/cap_trace.py` 只差分五维、`max_*`、`default_max_*`、あだ名、粉丝。
  10-31 的记录里同一事件还动 **マイル・長距離適性** 和 **多条 Hint Lv +2~+5**
  （`docs/机制对照表_20261031.md:352`）⇒ 本文的送分估值**漏了適性与ヒント两条腿，是下界**。

## 4 结论三（负面）：**驱动量没拆到公式 ⇒ 不接线**

按 AGENTS.md 的铁律，这一节是本文的落点。逐个排除：

1. **不是默认上限**：`dd` 20/20 全 0。
2. **不是「离上限还有多少」决定的**：`r(余裕合计, dm) = −0.387`（n=20，p≈0.09 不到显著），
   而且**符号是反的**——余裕越小抬得越多，跟「填满剩余空间」的规则方向相反。
   硬反例：201 t31 余裕 7393 → `dm` 12；204 t31 余裕 7132 → `dm` 27（余裕几乎一样，抬幅差一倍多）。
3. **不是现值决定的**：`r(現値合计, dm) = +0.390`（同样不显著）。同一条 t31 上，
   現値合计 2027 给 `dm` 12、2288 给 27、2326 给 16 ⇒ 现值涨、抬幅先涨后跌，没有单调关系。
4. **不是卡组决定的**：run 201 / 202 / 203 / 204 **卡组完全相同**（起点上限都是
   `[2234,1854,1800,1732,1800]`），每局 `dm` 分别是 **23 / 32 / 29 / 46** ⇒ 同卡组
   不同金额。唯一的共同变量是**继承双亲**不同：`(61,783) (61,787) (61,791) (61,795)`。
5. **不是玩家选择**：20/20 同一分支同一选项。
6. **不是发表会**：发表会四场效果表里没有抬 `max_*` 的行（#16 已逐格核过）。

**不推翻 LF靶子 §2b 那条「继承因子被排除」**：那条测的是**有没有**继承因子
（「逐因子对比有 vs 无的速度超上限量，均值只差 1 点」），本事件在 10/10 局里都存在，
落在「有」那一侧 ⇒ 两次测的是不同问题，不冲突。本文的变量是**双亲是谁 / 抽到哪些因子**，
不是**有没有因子**。

**找到了相关物，但方向没定住**。唯一随收益一起动的观测量是报文里的
`event_effected_factor_array`：

- **只在这一事件出现**：对照实验 = 把 run170 从 t1 到 t33 的每一条响应报文都查一遍，
  `event_effected_factor_array` 在非事件报文里**全为空**（`#0`），只有 t31 / t55 两条有内容 ⇒
  不是常挂的存档字段。
- 结构 = **6 个槽位**，`position ∈ {10, 11, 12, 20, 21, 22}` ⇒ 看着正是**双亲 × 3 组因子**
  （与「驱动变量是继承双亲」一致）。
- 因子总数 23–51，252 个不同 `factor_id` **全部命中** `master.mdb` 的 `succession_factor`
  （2,649 行），`level` 全为 0。
- 与收益的相关（`cap_trace.py` 默认输出末尾直接打这两个 `r`）：
  `r(#fac, dm) = +0.673`，`r(#fac, ds) = +0.665`（n=20）；
  只数適性/青色因子则 `r = +0.150 / +0.029`（无效，手算）。

但**它不能当输入用**：同一局里双亲完全相同 ⇒ 因子库存应当固定，而 t31 → t55 的条数在动
（168: 35→50，169: 38→45，170: 41→35，202: 23→32），且**符号不一致**
（169 因子变多 38→45，`dm` 却从 32 掉到 26；`ds` 从 204 掉到 170）
⇒ 这个数组更像**「这一掷抽到了哪些因子」的输出清单**，不是**决定这一掷大小的输入**。
拿输出回归输入是自证循环，所以本文不把它写成公式。

**顺带修一条 10-31 的连接键**（`docs/机制对照表_20261031.md:352` 记「连接键未通」）：
`succession_factor.effect_group_id` 连的是 **`succession_factor_effect.id`**（18 个 distinct
值 **18/18 命中**），不是 `factor_group_id`（那个只有 8 个交集，所以当年看着「不通」）。
拿这条键把 20 个样本里 252 个因子的 `target_type ∈ 1..5` 的 `value_1` 加起来当自变量：

| 对照 | 值 |
|---|---|
| `r(Σ因子value_1, dm)` | **+0.732**（n=20，比裸条数 +0.673 更强） |
| `r(Σ因子value_1, ds)` | +0.575 |
| Σ因子value_1 范围 | 110–244（均值 160） |
| 实测 `dm` 范围 | 11–42 |

**仍然不接**，两个硬理由：
1. **不成比例**——Σ=185 给 `dm` 24（run168 t31），Σ=185 也给 `dm` 33（run170 t55），
   Σ=244 给 42、Σ=111 给 11 ⇒ 没有 `k` 或分段能一次过 20 个样本（想拟合就是违规，不做）。
2. **`target_type` 的语义没定**——`factor_id 101`（速適性 ☆1，`factor_group_id = 1`）
   连出来的行是 `target_type = 2`，速適性给「耐」成长说不通 ⇒ 我按 `target_type` 当五轴
   去读是**猜的**，且 2,309 个带 `1..5` 行的因子里绝大多数是白因子（游戏里给**成长率 %**，
   不是直接加值）。拿语义没核实的字段去算绝对值，算出来的相关不能当证据。
   ⇒ 要往这条线走，**先定 `target_type` 与 `value_1/value_2` 的真实语义**，不是先拟合。

**还差的那块数据在客户端拿不到**：服务端要算的是双亲的五维/因子强度，但
`succession_gain_info_array = null`（20/20），继承报文里只有
`chara_info.succession_trained_chara_id_1/2` 两个 id。其它报文族
（`user_info_summary.user_trained_chara_array`、`partner_chara_info_array`、
`directory_card_array[].trained_chara`）里确实有 `trained_chara_id`，但那是**另一套 id 空间**
（见过 3520 / 4412 / 6607 / 6631 / 6635 / 6634），和 `chara_info` 里的 668 / 502 / 61 **对不上**，
用现有报文库无法把双亲的属性取回来。

## 5 裁决与对 LF 的意义

**留档，不接线**：本事件机制**没拆到公式**，按「禁止用拟合系数凑分」——
不写进 `data/`、不加配置开关、不在 `crates/` 里造通道。上面 §4 的六条负面 + §4 结尾
的「输入不可得」就是这个裁决的依据。要接线，缺的是**一手数据**（继承双亲的五维/因子表），
不是算力。

**LF 那 2,781 分不归这条通道**。LF靶子 §2b 原文把「练满初始上限只到 60,845、缺 2,781 分」
挂在上限上，量级核对结果：
- 这条通道的**带宽分**每局只有 **790**（乐观上限），填不满 2,781；
- LF靶子 §2b line 76 的**卡组起点抬升**本身就值 **≈ +2,743 分** ⇒ 2,781 的缺口主要已被
  起点上限解释，不是缺这条事件；
- 这条通道真正的大头是**送分**（每局 **1,604**，均值口径）。

**结构性错配（这才是给决策层的提示）**：引擎现在完全没有这条送分腿。以门禁锚点 run179 为例，
真机在这两格里送了 **266 五维和**（t31 180 + t55 86），引擎一个都没有；而 #16 后的 B 臂五维和
均值是 **7,960.4 / 7,963.1 / 7,968.4**（三个 seed，`out/crn_gate_cp4b.tsv`）vs 锚点 **8,041**
⇒ 只差 **−72 ~ −81 和**。两个数摆在一起 ⇒ **非送分通道在超产**（量级与这 266 相当）。
超产和缺产互相抵掉，总和对得上锚点，但**逐回合的「训练 vs 事件」取舍会被系统性偏置**——
缺的那 266 和**集中在 t31 / t55 两格**，超产摊在整局。
⚠️ 口径提醒：这是**引擎均值 vs 单局真值**，且门禁对锚点在**同一侧** ⇒ 按规范算**产出计、不可结论**；
上面那句「超产」是两条腿的量级对照，不是一次合格的配对检验。要坐实得做**逐回合**差分，
不是终局和。**这个错配不是拟合能修的，也不该用旋钮压平。**
