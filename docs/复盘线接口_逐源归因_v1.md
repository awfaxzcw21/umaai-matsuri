# 给复盘线的接口：逐源归因导出 v1（`attribution_v1.json`）

对应复盘方案 `review_improvement_plan_2026-11-06.md` §4.3 第 4 条「**没有分环节归因**」——
这半边我们已经做完了（#80，`docs/PT缺口逐源_20261106.md`），所以不该再造一遍。
本文件就是**消费说明书**，重点是最后两节的「不能拿来干什么」。

## 1 怎么生成 / 在哪

```
python E:/HJM/umaai-matsuri/tools/export_attribution.py            # 默认：run 170、面板 turn≥30
  --dumps 'E:/HJM/umaai-matsuri/out/ptledger/dump_s*.jsonl'        # 插桩 matsuri-dist 的 MC_DUMP
  --run 170 --turn-from 30 --out E:/HJM/umaai-matsuri/out/attribution/attribution_v1.json
```
产物约 **101 KB / 237 条真机窗口 / 128 个引擎 (turn,源) 桶**。`out/` 是 gitignore 工作区，
**要传给别人就传这个 JSON 本体**，别指望对方机器上有 dump。

生成物自带**导出自检**，两行必须都是 `差 +0.0`，否则这份不要发出去：
```
引擎 Σ(局均正差分) 5062.9（#80 基线 5,062.9 ⇒ 差 +0.0）
真机 Σ(正差分)    6486.0（#80 基线 6,486.0 ⇒ 差 +0.0）
```

## 2 回合号约定（最容易接错的一处，先读这段）

`turn0 = 0 基 = 面板回合 − 1 = 引擎内部 turn`。**和你们 `actions[].turn` 的约定是同一个**
（方案 §5.0：`turn` 0 基 ＝ `current_turn − 1`），所以直接对 `turn0` 就行。

一手自证（不是猜的）：cap-10 锚点 `_state_t30_cap10.json` 的 `turn=30`（面板口径），
该局插桩 `ptrace` 第一条落在 **turn 29**。导出里两侧都同时给了 `turn0` 与 `turnPanel`，
要回到报文原值就用 `turnPanel`。

| 位置 | 字段 | 含义 |
|---|---|---|
| 顶层 | `schemaVersion` | 契约版本，现为 **1**；加字段不删字段，删/改语义才升版 |
| | `turnConvention` / `attributionRules` | 上面两节的机器可读版 |

| `realWindows[]` | `source` / `endpoint` | R1–R8 源名 ＋ 给复盘线用的通道别名（`exec_command`/`check_event`/`race`/`check_point`/`skill_purchase`/…） |
| | `dPt` `prePt` `postPt` `dSkills` | 窗口差分（**整笔记给该窗口的请求**，含同窗口自动触发的心意继承/演目升级） |
| | `channel` `commandId` `eventId` `run` `file` | 一手出处，可回查到具体报文文件 |
| `referenceTrajectory.engineByTurnSource[]` | `turn0` `source` `windowsPerGame` `ptMeanPerGame` | 引擎侧**局均**参考轨迹（300 局平均），就是你们缺的那条「参照线」的引擎版本 |

归因实现只有一份：真机侧走 `tools/pt_ledger.py::source_of`（R1–R8），
引擎侧走 `tools/engine_pt_ledger.py::src_of`。本次为了接这个导出把两处从 `main()` 里提出来做成函数，
**行为零变化**（`ledger_summary.csv` 重构前后逐字节相同；逐源表仍 1,379.3／26.1／0／191.0／−173.3）。

## 5 不能拿来干什么（这条是本接口的主要用途）

`calibration.status = "未校准——可以当描述，不可以当玩家责任"`。三条已知引擎偏差（都是本周实测）：

1. **PT gross −17.1%**（真机同段 6,486 vs 引擎 5,062.9）。
2. **稽古单手率 72.8 vs 真机 121.3**＝缺口的 77%；**软上限已实测排除**（关掉后降到 66.8，方向相反）。
3. **引擎里没有「技能清单」这个对象**——技能分只由存量 PT 过曲线（`mod.rs:1717`），
   而真实技能分有 **40% 不吃 PT**（金技能 26.7% ＋ 固有系 13.3%）。

⇒ 因此 `doNotUseFor` 里写死了三条：
**「你本可以拿 X 分」/理论可达上限**（会把引擎偏差洗成玩家损失）、
**regret 的绝对值**（同随机流下的相对差可以，绝对期望分不行）、
**任何需要技能清单级粒度的判据**（引擎侧没有那个对象）。

方案 §5 的 P2「受约束理论上限」如果要吃这份数据，**必须显式带上 `calibration` 一起渲染**，
不要只取数字。P1 的「累计 delta」用 `referenceTrajectory` 没问题——它就是同口径的参照线，
但文案上要说「引擎参照」，不能说「你的上限」。

## 6 与方案其余阶段的对应

| 方案阶段 | 这份导出给了什么 / 还缺什么 |
|---|---|
| **P0 实测动作替换推断** | 缺的是你们 `actions[]`（E2），**不在这份里**；这份的 `realWindows.commandId/eventId/file` 是同一批请求的**另一面**（PT 差分侧），两边可以对表互相验证 |
| **P1 参考轨迹＋累计 delta** | `referenceTrajectory.engineByTurnSource` 直接可用（引擎侧参照） |
| **P1 逐回合 regret** | 相对差可用；绝对期望分受 §5.2/5.3 限制 |
| **P2 理论上限** | **暂不建议接**，等引擎技能清单与稽古率两条修完 |
| **P2 跨局 PB** | 与本接口无关 |
