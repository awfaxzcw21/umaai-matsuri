## 1. 结论（四句）

1. **PT 缺口 −417/局 不是公式欠**：`(kind, 卡组参与人头)` 同格子对照下公式项 **+20 Pt/局**；
   人头=0 那格两边逐位相等（真机 7.9 = 引擎 7.9）。缺的是**手数 +547 / 人头分布 −985**。
2. **五维缺口 −275/局 才是公式欠**，且**全在稽古 home 腿**（−335，普通训练反而 +61）：
   同格子下引擎每手少 10–14 点五维而 PT 持平甚至更高 ⇒ 缺的是**稽古 base 的五维抬升**。
3. **−985 的人头分布 65% 责在选位策略**：引擎盘面有 1.84 人头的最满位，自己只落 1.03
   （落子/最满 = **0.56**）；真机盘面 2.10、落子 2.00（= **0.95**，取最满 73–88% vs 引擎 34–37%）。
4. **另有一条完全没建模的机制（占 19%）**：`sub_command_partner_array` 的**追加参与**——真机落子命令上
   2.34 人头里有 0.34 来自追加，引擎只数站在自己位上的卡，追加=0。

站位模型本身**不是**主犯（只占 16%）：每板放卡 真机 4.66（非合宿）/6.00（合宿）vs 引擎 4.54（−9%/−24%），
最满位站位人头 真机 2.084/2.146 vs 引擎 1.837（−12%/−14%）。

## 2. 口径：两边到底在比什么

| 项 | 真机 | 引擎 |
|---|---|---|
| 可比量 | `home_info.command_info_array[cid].params_inc_dec_info_array` 里 `target_type=30`（稽古的这条 = **home 腿**，#34 已用 227/229 手恒等式钉住） | `MatsuriGame::training_leg(idx)`（`crates/matsuri-core/src/game/mod.rs:559`），稽古在 `do_keiko_impl` 里调它当 home 腿（`mod.rs:1469`） |
| 分桶键 | **卡组参与人头**：`training_partner_array` 里 `<100` 的个数 | 只数 `PersonType::Card`（引擎 `base.distribution` 把所有 person 类型都装进来，`>=100` 那侧不同名） |
| 为什么不用 Lv | 板上报文 `level` 对 101–106 是训练 Lv、对 5101–5105 是**演目 Lv**，两边不同义 | 记的是训练 Lv |
| 窗口 | 引擎回合 30–78（面板 31–79），完整局 = 段内训练手 ≥20 ⇒ **6 局**（4 个被截断的 run 剔除） | 4,000 局，同一测量壳同一基策（`MatsuriRolloutTrainer`） |

**两条必须写清的语义（本轮新发现，之前都算错过）**

- **真机的 510x 稽古板 ≠ 合宿板**。`home_info` 里 5101–5105 大量出现在非合宿回合
  （窗口内 1,162 条非合宿 vs 400 条合宿）：演目槽点亮就走稽古。合宿标记只能取
  `festa_data_set.festa_info.summer_camp_remain_turn_num > 0`。
  ⇒ 之前那句「真机稽古密度 1.81 vs 引擎合宿 0.91」拿的是两个不同总体，**作废**。
- **同一块板上 101–106 与 5101–5105 共存且互补**：某位被点亮时，卡报在 510x 条目上，
  该位的 10x 条目人头为 0（窗口内 66% 的 plain 条目人头=0）。
  所以**不能**拿「板上条目数」当「物理训练位数」。
- **人头还会重复**：同一张卡既算自己站的命令、又作为 `sub_command_partner_array` 追加进另一条
  命令 ⇒ 每板 Σ参与 > Σ去重（2,372 块板里 1,303 块如此，均值 6.53 参与 vs 5.16 去重）。
  这不是统计错误，是**追加参与**机制；但它使「每命令人头」和「每站位人头」是两个不同变量，
  本文把两列都分开算（`heads_deck` = 参与，`heads_own` = 站位，`heads_sub` = 追加）。

⚠ **别拿「每条目人头」去比 `mean_slot_heads`**：真机一块非合宿板报 6.04 条命令（点亮位的 10x 条目
人头=0），引擎只有 5 个位 ⇒ 「4.66 卡 / 6.04 条目 = 0.77/条目 vs 引擎 0.91/位」这种「引擎反而更密」
的数是**单位错了**，不是密度差。可比的只有三种：**每板放卡总数**、**最满位人头**、**落子那人头**。

**乘法拆解**（落子参与人头 真机 2.339 vs 引擎 1.027 = **2.28×**；手/局 真机 30.0 vs 引擎 42.0）：

```
2.278 = 站位排布 1.143   最满位站位人头 2.10(加权) / 1.837
      × 选位增益 1.704   落子站位/最满位：真机 0.95 vs 引擎 0.56（引擎只取到盘面的 56%）
      × 追加参与 1.169   2.339/2.001，sub_command 那份，引擎恒为 0
```

按对数分份额：**选位策略 65%、追加参与机制 19%、站位排布 16%**
⇒ 之前那句「站位模型基本对，缺在选位策略」方向没错，但漏了追加参与这一整块机制，
且把 2.28× 全记在策略头上（实际策略占 65%）。每板放卡总数真机加权 4.99 vs 引擎 4.54（−9%）。

✅ #41 已复测（`docs/强策档盘面读数_20261104.md`）：换强策档（mccli 2-ply）后，同一配对口径的选位增益
只从 0.558 抬到 0.622（K=8）/ 0.637（K=16）/ 0.644（K=32），搜索已到平台而缺口 79% 仍在；
三层阶梯显示**实际落子 ≈ 引擎自己估值的最优格**（non_camp 1.193 vs 1.177），
所以缺口不在「策略没学到」，在**估值没给人头定价**（每多 1 人头只值整局分的 ~0.3%，τ=0.195）。
那个 1.704 因此是「估值低估」的账，不是「决策偷懒」的账。

## 4. 三项分解（`split3`，恒等式残差 ~1e-14）

```
缺口 = (N_e − N_r)·Σp_r·v_r  总手数效应
     + N_e·Σ(p_e − p_r)·v_r  人头分布效应
     + N_e·Σ p_e·(v_e − v_r) 公式效应
```

| 度量 | 总手数 | 人头分布 | 公式 | 合计 |
|---|---|---|---|---|
| Pt | **+547** | **−985** | +20 | −417 |
| 五维和 | **+669** | **−669** | **−275** | −275 |

分 kind：

| 腿 | Pt 总手数 / 分布 / 公式 | 五维 总手数 / 分布 / 公式 |
|---|---|---|
| 普通训练 home 腿 | +279 / −306 / +37 | +344 / −233 / +61 |
| 稽古 home 腿 | +268 / −679 / −16 | +325 / −436 / **−335** |

- Pt 公式 +20 ⇒ **#39 那句「每手只有真机一半」不成立**；它是把「引擎多打 12 手低人头训练」
  和「真机每手站 2.3 人」平均到一处产生的假象。
- 五维总手数 +669 与人头分布 −669 **恰好抵消**（不是互证，是两个大项反号相加）；
  剩下 −275 全在公式，且集中在稽古 home 腿。

## 5. 稽古 home 腿缺的那一刀（线索，**未接进引擎**）

零参与人头档（`heads_deck == 0`，窗口内中位）：

| 层 | n | Pt | Σ五维 | Pt/五维 |
|---|---|---|---|---|
| 真机 稽古（演目 Lv 2） | 152 | **15.0** | **33.0** | 0.455 |
| 真机 普通训练（训练 Lv 1） | 685 | 6.0 | 13.0 | 0.462 |
| 引擎 稽古 home 腿 | 5.27 手/局 | 8.2 | 19.5 | 0.42 |
| 引擎 普通训练 home 腿 | 3.04 手/局 | 7.9 | 19.2 | 0.41 |

三件事同时成立：

1. 真机稽古 home 腿 = 同板普通训练的 **2.5×**（Pt 和五维**同比**，比值不变）⇒ 是 **base 抬升**，
   不是 PT 独有乘区。
2. 引擎的稽古 home 腿 ≡ 普通训练 home 腿（8.2 ≈ 7.9）⇒ **完全没有这个抬升**：
   `do_keiko_impl` 把 home 腿写成 `self.training_leg(idx)`（`mod.rs:1469`，用的是 10x 训练 base），
   而 510x 那张 base 只喂给**演目腿**（`keiko_basic_value` → `value` → `act_pt_leg`，`mod.rs:1462-1472`）。
3. 表证据方向对、**量级不够**：`master.mdb` scenario 15 里
   `single_mode_training` 5101 SP=9/体力−25/五维[16,·,3] vs 101 SP=7/−20/五维[12,·,2] ⇒ 只有 1.29/1.33×，
   离实测 2.5× 还差 ~1.8×，那 1.8× 现在**没有表来源**（怀疑是稽古/合宿自身再乘一档，未证）。

⇒ 这条**足以解释 #39 的 home/演目 72:28 vs 真机 47:53**（引擎把唯一一份 510x 抬升记在演目腿上），
但在 PT 侧被别处抵掉（公式项只 −16），在**五维侧**留下 −335。
**不许**按 2.5× 反乘任何系数进 `data/`；下一刀是把 510x 的 `single_mode_training_effect`
按 (result_state, sub_id) 摊开找那 1.8×，或直接拿合宿期同 Lv 同人头的普通训练做对照。
