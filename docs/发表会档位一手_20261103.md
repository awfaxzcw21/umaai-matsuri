## 2 结论一：档位 = `min(全演目 Lv) ≥ need`，到回合必结算

`check_point_result_array[].result_type`（1=成功 / 2=大成功）与结算前的
`festa_data_set.act_info_array[].level` 逐样本对：

| 场次 | need（表） | 成功档 minLv | 大成功档 minLv |
|---|---|---|---|
| #1 | 3 | 2（n=5） | 3（n=5） |
| #2 | 5 | 3–4（n=4） | 5–6（n=5） |
| #3 | 6 | 4–5（n=4） | 6–8（n=5） |
| #4 | 表内无行 | 4–5（n=4） | 6–9（n=5） |

**28 对 / 0 错**（只有前三场有表内 need 可判，故 28 = 5+5+4+5+4+5）。
关键是 **`min == need` 就是大成功**（run168 t48 Lv `[5,5,5,5,6]` → 大成功、run179 t68/t78
`[6,6,6,6,6]` → 大成功），旧引擎规则要求**全演目严格大于 need**，所以这两局被判成成功档。

**第 4 场的 `need = 6` 是夹逼出来的，不是猜的**：规则形状一旦定为「min ≥ need ⇒ 大成功」，
成功档里最大的 minLv = 5 ⇒ `need > 5`；大成功档里最小的 minLv = 6 ⇒ `need ≤ 6`
⇒ `need = 6` 是唯一整数。同一个方法回头验前三场，复现表里的 3 / 5 / 6（逐场
成功档 max 与 大成功档 min 正好夹住），所以规则形状本身是被验证过的。

**到回合必结算**：10 局 × 4 场里，每一场都在面板回合 24 / 48 / 68 / 78 出现结算，
没有「Lv 不够就不给奖励」的样本（最低的那批拿到成功档 = 100–150 PT）。旧引擎把
「全演目达标」当成结算的前置条件 ⇒ 低 Lv 局直接拿 0 PT，这是双重错（既挡了结算，
又把边界写成严格大于）。

## 3 结论二：全能力奖励吃 1200 压缩——**第 4 场大成功是例外**

`pre = post − d_stats` 还原结算前五维，按「名义值 / 引擎压缩公式应得值」分类
（`compress(pre, nom) = min(nom, max(0, 1200−pre)) + ⌊(nom − 那一段)/2⌋`，与 `soft_cap_gain` 同款）：

| 场次 档 | 线下满额 | 跨线压缩 | 跨线未压 | **线上压缩** | **线上未压缩** | 其它 |

| #1 大 | 25 | 0 | 0 | 0 | 0 | 0 |

- **`pre ≥ 1200` 的轴：前三场 27/27 减半、第 4 场成功档 4/4 减半；第 4 场大成功 0/25 减半。**
- 那 3 条「其它」全在第 4 场大成功，且都**撞 `max_*` 硬顶**：`pre=2299, max=2299 ⇒ +0`、
  `pre=1844, max=1845 ⇒ +1`、`pre=2279, max=2293 ⇒ +14`。也就是说这一档给的是**满额 15**，
  只是被硬顶截断 ⇒ 实际是 **25/25 未压缩**。
- 「跨线压缩」2 条（run169 / run170 t68，`pre=1194 / 1195`、名义 15、实得 10）
  确认压缩是**分段**的：只减 1200 以上那一段，不是整条减半。

⇒ 这是一个**观测事实，机制未解释**。为什么同一场的成功档压缩、大成功档不压缩，报文读不出来
（没有可读的通道标记）。处理方式：`CheckPointDef.great_no_soft_cap` 只给第 4 场开这一个口子，
**不推广成全局规则、不写成开关让玩家调**。如果后续样本（≥ 一个反例）推翻，就改这一场。

## 5 buff 腿：第 4 场没有一手行 ⇒ 留 `null`

（`docs/glossary.md` 决策表 + `check_point_buffs_are_cumulative_totals`）。

**顺手否掉一条旧归因**：`single_mode_15_check_point_effect` 全 20 行的 `effect_type` 只有

（t31/t55 也不是发表会回合 24/48/68/78）。那两处抬升「不是训练溢出」仍然成立。
**落点已由 #37 找到**：剧本级事件 `story_id 400000040`「心意的继承」（t31 / t55 各一次，
