> 的可建模对象。本文只写**一手报文 / master.mdb 能查到的事实**，以及查不到的部分。

## 二、报文证据

原始报文在 `E:/HJM/jidianbeiAI0.22/out/hachimi_raw`（5591 个 msgpack），
解码用同仓 `msgpack_lite.py`；`race_entry.py` 是这个项目里现成的「自选比赛解码」实现。

### 2.1 本局可报名的比赛

开局 / 读档那类响应里挂 `single_mode_load_common.race_random_program_array`：

```json
[{"turn": 45, "program_id": 1110}, {"turn": 45, "program_id": 1111}, {"turn": 45, "program_id": 1112},
 {"turn": 69, "program_id": 1113}, {"turn": 69, "program_id": 1114}, {"turn": 69, "program_id": 1115}]
```

- 34 局报文**结构完全一致**：面板回合 45 / 69 各 3 场。
- 每局抽到的 `program_id` 不同（随机抽）：`1110~1118` 这 9 个 G1 program 里，
  45 窗口抽 3 个、69 窗口抽 3 个（个别局抽到 `1024~1026`）。

### 2.2 报名状态

`chara_info.reserve_race_program_id` = 本回合报名的 program；**1937 份回合报文里恒为 0**
⇒ 这 34 局玩家一次都没报名自选比赛（`race_program_id` 非 0 的那些回合都是**目標赛**）。

### 2.3 粉丝数不是拦路虎

窗口回合的粉丝数在 59,830 ~ 456,416 之间，**远高于 12,000 的报名门槛**
⇒ 玩家没报名是**选择**，不是被门槛挡住。（本机引擎没有粉丝系统，见 §五。）

## 三、master.mdb 侧

| 表 | 用途 |
|---|---|
| `single_mode_program` | `id` → `need_fan_count` / `month` / `half` / `race_instance_id` |
| `race_instance` | `id` → `race_id` |
| `race` | `id` → `grade`（**100 = G1 / 200 = G2 / 300 = G3 / 400 = OP**）、`course_set` |

- 剧本 15 的自选池：`1110~1118`（G1，`need_fan_count = 12000`，`month = 11`、`half = 1`）。
- **GIII 的 program（`1125~1131`）月份是 1 / 4 / 7 / 8 / 12，没有 11 月前半的**
  ⇒ 剧本 15 的两个窗口只可能抽到 G1 ⇒ **GIII（1 ステ +8 / PT +35）在剧本 15 不可达**。
  （memo 记的 GIII 规则本身没错，只是剧本 15 这两个窗口够不着。）

## 四、奖励口径（memo + 两例真机反解）

memo §8.1：目標外 GI = **1 ステ +10 / SP +45**。

真机两例（`docs/机制对照表_20261031.md`）：`体力 −15 / 耐 +15 / PT 69` 与 `体力 −20 / 賢 +15 / PT 69`。

- **「1 ステ」是随机项**：两例分别落在耐力与智力 ⇒ 随机，不是固定项。
- 数值与二段式乘区自洽：`floor(floor(45 × m卡) × m_cp) = 69`、`floor(floor(10 × m卡) × m_cp) = 15`
  在 `m卡 = 1.0、m_cp = 1.55` 时同时成立（与目標赛同一条二段式口径）。
- **体力代价 −15 / −20 两例不一致**，来源未查明 ⇒ **未建模**。
