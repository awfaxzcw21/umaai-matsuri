## 三条口径（先说清，否则后面的数没法读）

1. **窗口 = 相邻两个「局内请求」之间的全部结算报文**；pre = 请求前最后一个 `chara_info`
   快照，post = 下一请求前最后一个 ⇒ 差分**不跨请求**，不会把事件增益混进训练差分
   （跨回合差分是已知陷阱）。只统计 `same_run=1` 的窗口，跨局边界剔除（12 个）。
2. **PT 按「累计获得」（正差分毛增）统计，不是余额。** 引擎的 `skill_pt` 只增不减
   （没有购入花费模型），门禁锚点同样是累计口径 —— 见下面「锚点口径核对」。
3. 样本 = 8 局整局、603 个 `(run,turn)` 观测点。

## 判读

1. **稽古这条源（36.3% 毛增）引擎此前只算了一条腿。** 报文逐手核对：229 执行手里
   `d_sp == home[30] + p[30]` 命中 227 手，home 腿均值 48.3、festa 腿 55.2（⇒ 每手 103.5，
   与本表 mean/手 99.4 同量级，两条独立路径互相印证）。home 腿占这条源的 46.7%
   ⇒ 全 corpus 约 **17% 的毛增 PT** 是凭空缺的。这一条已由 `f1db6e8` 接上。
2. **比赛是最大头（38.5%），而且 PT 是赛事结算给的、不是请求给的** —— R5 判据明细里
   `eid=7005` 83/83、`eid=1011` 35/35、`eid=101002/101004/101006` 各 8/8 都是 rate=1.00。
   引擎侧走的是已定案的二段式 floor 乘区（见 `docs/` 赛后奖励定案），这块与稽古无关。
3. **外出 36 个窗口 PT 恒为 0。** 引擎若有「外出给 PT」的路径，那是错的，本表可当反例。
4. **技能购入是真机花掉 PT 的唯一通道**：账本只抓到 2 个窗口、每手 −8,370。引擎**没有** PT
   花费路径（连 PT 上限都没有），所以引擎侧只能对「累计获得」，不能对余额。
   —— 而且购入并不罕见：8 局里 **3 局**（run170/171/179）末余额是 1/2/8，
   就是整局攒的 PT 全花在技能上了。
5. **未归因 −8,334 全在 run171**（净残差落在 15 个 `(run,turn)`，占 2.5%）。
   该局毛增 8,006 + 开局 ≈ 8,364、末余额 2 ⇒ 这 −8,334 就是**第三笔技能购入**，
   只是它落在没被 `same_run=1` 窗口覆盖的位置上（扫描器漏采，不是新机制）。
   `|残差|` 合计 11,634 = 毛增的 20.7%，但另外 7 局残差为 0 ⇒ 不去拿它调任何系数。

## 锚点口径核对（为什么门禁 PT 能当累计用）

run179 的账本：正差分合计 441 + 1,250 + 2,937 + 2,923 + 398 = **7,949**，加开局初始
（全 corpus 均值 357.6）≈ **8,306**；门禁锚点 = **8,339**（差 33，在残差范围内）。
同一局报文的**余额**末值 = 8（峰 7,654），因为有 −8,311 的技能购入。
⇒ 门禁与引擎 dump 的 `pt` 都是累计获得口径，对得上；拿余额比会差一个数量级。

顺带把 run169/172/201 也对了一遍：毛增 + 开局 与末余额逐局差 ≤ 35，都吻合。
