# 计分口径待裁决 —— 2.35 拟合系数问题

> 2026-11-02 建档，同日拿到 LF 卡育成情報截图后**压缩口径已裁决**（§3.1）；技能项对 PT 的线性假设**已被否**（§3.2）。
> 仍开放的见 §3.3 / §3.4 与 §6。本文只登记证据，不用系数凑分。
> 相关：[[reference-score-rank-table]]、`docs/量后决_matsuri档_20261102.md` §4、`docs/机制对照表_20261031.md` §9.1。

## 1. 现在并存三套「五维 + PT → 评分」

| 口径 | 公式 | 出处 | 含拟合？ |
|---|---|---|---|
| 引擎原生 `score` | `Σ status_final_score(min(五维, 上限)) + 2.0×total_pt + skill_score` | `umasim/src/game/uma.rs:226 score_parts` | 否，但 `skill_score` 在模拟里是**常数 510**（`uma.rs:193`「固有按5星计算」） |
| 面板 `real_score` | `Σ status_final_score(revise(五维)) + 1.0746 × round(skill_pt × 2.35)` | `crates/matsuri-cli/src/dist.rs:136-139` | **是**，2.35 与 1.0746 都是拟合 |
| 社区回归式 | `4.682 × Σrevise(五维) + 2.46×PT` | `docs/plan/intake.md:263` | 是（三点锚回归） |

`revise(v) = v (v≤1200) / 2v−1200 (v>1200)`（`dist.rs:67`）——它假设**引擎内部五维就是客户端显示值（已压缩）**，
所以查表前先做逆变换还原。**这条假设 2026-11-02 已被 §3.1 的双卡联立证实**（客户端计分用压缩前原始值）；
但它反过来给 §3.3 第 1 条制造了一个新问题：如果我们的 `soft_cap` 把内部值本身压掉了，再 `revise` 就是二次还原。

## 2. 2.35 是什么来历（源码自己的话）

`dist.rs:38-55` 注释原文，逐条抄：

- 黑板全样本聚合口径 `REAL_GRADES_PER_PT = 2.61`（137 匹练成马娘 24,114 grade / 9,240 pt）；
- 本剧本可核的那一局（card 114101，t78 五维 2244/1750/1845/1349/1296、PT 8,450、官方 `rank_score` 72,142）
  反推只有 `18,297 / 8,450 = 2.17`；
- 直接量到的 Σgrade 19,492 给 `2.31`；
- **取中间值 2.35，使 72,142 的残差落在 1% 内**。
- 注释自己标注：⚠「**这个数是拟合出来的，不是量出来的机制**（2026-10-31 标注）……不要拿它当门禁」。

还有第二个没定的分叉：**2.35 该除「总得到 PT」还是「实付 PT」**。本机收的一局（PT 8,339 / 实付 7,649 / Σgrade 17,022）
按总 PT 是 2.04、按实付是 2.23，**两个都不到 2.35**。

⇒ 结论：2.35 是一个**为对齐 72,142 这一个锚点而定的标量**。它的合法使用范围就是 72,142 附近，
外推到 91,400（+27%）没有依据。

## 3. 拿 LF 卡做交叉验证（2026-11-02 新证据）

分数线表本地有两份独立一手数据，**逐档一致**（148 档到 105,399 完全相同，只在 LE 以上插件把 LE..LS24 合并成「LE以上」）：
`E:/HJM/umaai_next/gamedata/constants.json`（`rank_names`/`rank_scores`，298 档，末档 LS24=190,400）
与 `E:/HJM/_ref01/matsuri-ref-01/data/rank_table.json`（源 URA-Plugins `GradeRank.cs`）。
**LF 起线 = 91,400；LF4 = 93,800–94,399；LF5 = 94,400。**

### 3.1 双卡联立：压缩口径已裁决（2026-11-02 拿到育成情報截图）

LF 卡 **獲得スキルPt = 10,961 / 評価点 = 94,372**（18戦18勝、合計演目Lv 46、ファン 527,563、登録日 2026-11-01、
育成シナリオ「朋、史解き ―駿大祭―」＝本剧本）。拿它和已知的 72,142 那局（五维 2244/1750/1845/1349/1296）联立，
两套假设各算一个「每 PT 折算评分」：

| 假设 | 72,142 那局（PT 8,339 / 8,450） | LF 卡（PT 10,961） | 判定 |
|---|---|---|---|
| (a) 显示值直查表 | 4.82 / 4.76 | **5.21** | ✗ 无任何已知口径在此量级 |
| (b) `revise` 还原后查表 | **2.610** / 2.576 | **2.805** | ✓ 与黑板聚合 `2.61` 吻合 |

⇒ **裁决：客户端计分用压缩前的原始值，显示值只是减半后的展示**（即上游 `量后决` §4 那条说法成立，
我们 `real_score` 的 `revise` 方向正确）。(b) 下 LF 卡的五维分 = 63,626、残差 = 30,746、÷10,961 = 2.805。

### 3.2 结算：公式是加性线性的，不线性的是「PT→Σgrade 汇率」（2026-11-03 定）

LF 卡逐技能 Σ 已经数完（`out/_lf_resolved.json`，115 条，Σgrade **28,718**）：

```
63,626 (五维分, revise 口径) + 1.0746 × 28,718 = 94,486   vs 实机 94,372   ⇒ +0.12%
```

72,142 那局用**当前** `constants.json` 重算：五维分 50,373 + 1.0746×实测 Σgrade 19,492 = **71,319**
vs 实机 72,142 ⇒ **−1.1%**。两局各自独立对上同一套加性公式 ⇒

1. **公式本身成立**：`評価点 = Σ five_status_final_score[revise(显示值)] + 1.0746 × Σgrade`，
   两局误差 ≤1.2%，不需要任何额外项。
2. **旧 2.35 错在两头都脏**：它是拿**旧表**的 53,845（比现表高 3,472）反解出来的，
   所以「贴 LF 要 2.610、贴 72,142 要 2.35」不是非线性，是**同一个数被两张表各自拽偏**。
3. **真正不恒定的是汇率**：LF 卡 28,718/10,961 = **2.6200**，72,142 那局 19,492/8,450 = **2.31**，
   黑板 137 匹聚合 = **2.6097**。汇率随购买策略浮动 2.31–2.62，同一份五维能差出 ~2,800 评分。
   ⇒ 这不是评分公式的问题，是**购买决策没建模**的问题；调系数收窄不了。

### 3.3 两条待查项：第 1 条已结，第 2 条降级为纯表版本问题

1. **软上限接线位置——已核对，`revise` 是单次还原，没有二次**：
   `constants.json` 的 `five_status_limit_base` = **[3100, 2400, 2200, 2200, 2400]**（和 12,300），
   这正是**压缩前**尺度（= revise 后的表索引域，上限 3801）；而 `game/mod.rs:487` 的
   `soft_cap_gain` 压的是**增量**（「超出 1200 的部分减半」），累加出来的 `five_status` 是**显示值**。
   存的是显示值、`revise` 的入参要的也是显示值 ⇒ 单次还原，方向正确。
   反证：若 `five_status` 是原始值，直查表给 LF 上限只有 **36,757**，比实测 63,626 低 42%。
2. **gamedata 版本漂移**：`dist.rs` 旧注释的 53,845 vs 现表 50,373（差 3,472）仍在，
   但现在它只影响**历史拟合值的出处**，不影响 §3.2 的两局联立（那步已用现表重算并闭合到 −1.1%）。
   名次表实际 **298 档**（US8=72,900 / LF=91,400，已按现表核对），`dist.rs:18` 的「301 档」是旧说法。

### 3.4 真技能分：已经有了，但引擎侧用不上

`MC_GRADE_PER_PT` 环境变量与 `GRADE_PER_PT_DEFAULT = 2.35` **已删除**，`real_score` 改用
量出来的 `GRADE_PER_PT = 2.61`（137 匹 2.6097 / LF 卡 2.6200 两个独立来源，预测 LF 总分
94,368 vs 实机 94,372，误差 −0.004%）。

但**逐技能 Σ 在引擎里做不到**：`grade_value` 在 `.rs` 里零命中，`constants.json` 没有技能价表，
模拟局跑完只有一个 `skill_pt` 计数——它根本没有「买了哪些技能」这个状态。
真实 Σgrade 只在**已打完的局**可从报文 `skill_array` × mdb `skill_data.grade_value` 数出来（LF 卡就是这么数的）。
所以「PT → Σgrade」这一步的正当来源是**购买策略**，而策略已经现成：
黑板 `tools/skill_plan.py`（0/1 背包，`_knapsack`，含下位→上位合并价、ヒント折扣、剧本 −4% 小切、
赛程/适性过滤）与插件包 `SkillTipsResponseAnalyzer`（CP-SAT）。
**接缝定在这里：引擎产 PT，背包把 PT 换成清单，评分表把清单换成 Σgrade。不要在 `dist.rs` 里再造一个汇率。**

## 4. 这个系数对「能不能凹到 LF」的影响（实测）

`matsuri-dist` 历史锚点扫描（`out/_dist_anchor_t*_s*.json`，n=2000/格；s1.0 与 s1.6 只差注入锚点五维，**PT 完全相同**）：

| 出发回合 | 五维和均 | real 均 | P(≥LF) |
|---|---|---|---|
| t15 | 6,612 / 7,211 | 44.5k / 51.7k | 0.00% |
| t20 | 7,795 / 8,423 | 62.9k / 71.6k | 0.20% / 1.10% |
| t30 | 7,822 / 8,380 | 62.9k / 70.7k | 0.90% / 6.70% |
| t37 | 8,769 / **9,312** | 77.5k / **85.6k** | 13.75% / **33.50%** |
| t45 | 9,146 / **9,468** | 82.9k / **88.0k** | 12.55% / 28.55% |
| t60 | 8,692 / 8,838 | 71.9k / 74.0k | 0.05% / 0.45% |

三条要记的：

1. **同一批采样换引擎原生 `score` 口径，P(≥US7) 全为 0%**（US7=71,600）。两套口径差 ~1.4 万 ⇒
   档位结论完全由口径决定，不由局面决定。
2. `real_score` 对五维和的敏感度 **≈ 15 评分 / 五维点**（+543 五维和 ⇒ +8,121 评分；
   >1200 段 `revise` 翻倍再乘表尾斜率 ~7）。所以冲 LF 的杠杆是**五维和站上 9,300**，不是 PT。
3. P(≥LF) 从 0.9% 到 33.5% 只靠「把注入锚点五维乘 1.6」得到 ⇒ 这个百分数是**假设局的相对趋势**，
   不是我们常规产出的达成率。真机 t78 那份 state（整局已打完，4000 次只在收尾抖）
   real 均 63,032 = UA9–US 档，P(≥LF) = 0%。

## 5. 铁律落点

- **门禁不看评分 / 档位 / P(≥LF)**。门禁只认 `gate` 里的三分量 `five_sum` / `stat_score` / `pt`
  （`dist.rs` 的 `gate` 块，三项都不含汇率），CRN 同种子逐局配对的贴近幅度 95% 区间。
- `real_score` 只允许用于**面板显示**。技能项现在是**量出来的聚合汇率 2.61**（不是反解拟合），
  必须同时带出 `grade_per_pt_basis` 里那句「逐局实测带宽 2.31–2.62」——把它当点位真值就是自欺。
- **拟合旋钮已从结构上删除**：`GRADE_PER_PT_DEFAULT = 2.35` 和 `MC_GRADE_PER_PT` 环境变量都不存在了，
  只剩 `const GRADE_PER_PT = 2.61`。想「调系数贴某个档位」现在必须改代码重编译，且注释里已经把
  两个独立出处和 −0.004% 的验证写死，改不动也赖不掉。

   清单归面板」。当前默认后者，但那样引擎自己永远答不出「这局能到几分」。
