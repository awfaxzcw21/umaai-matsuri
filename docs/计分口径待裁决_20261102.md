# 计分口径待裁决 —— 2.35 拟合系数问题

> 2026-11-02 建档。触发点：拿 LF 卡（94,372 / LF4）去核我们的评分口径，发现**档位判定 100% 取决于用哪套口径**，
> 而其中一套的核心系数是反解出来的。本文只登记冲突和裁决所需证据，**不裁决**。
> 相关：[[reference-score-rank-table]]、`docs/量后决_matsuri档_20261102.md` §4、`docs/机制对照表_20261031.md` §9.1。

## 1. 现在并存三套「五维 + PT → 评分」

| 口径 | 公式 | 出处 | 含拟合？ |
|---|---|---|---|
| 引擎原生 `score` | `Σ status_final_score(min(五维, 上限)) + 2.0×total_pt + skill_score` | `umasim/src/game/uma.rs:226 score_parts` | 否，但 `skill_score` 在模拟里是**常数 510**（`uma.rs:193`「固有按5星计算」） |
| 面板 `real_score` | `Σ status_final_score(revise(五维)) + 1.0746 × round(skill_pt × 2.35)` | `crates/matsuri-cli/src/dist.rs:136-139` | **是**，2.35 与 1.0746 都是拟合 |
| 社区回归式 | `4.682 × Σrevise(五维) + 2.46×PT` | `docs/plan/intake.md:263` | 是（三点锚回归） |

`revise(v) = v (v≤1200) / 2v−1200 (v>1200)`（`dist.rs:67`）——它假设**引擎内部五维就是客户端显示值（已压缩）**，
所以查表前先做逆变换还原。这条假设本身没被真机钉死，和「上游计分用原始值、显示才减半」那条冲突是同一件事的两面。

## 2. 2.35 是什么来历（源码自己的话）

`dist.rs:38-55` 注释原文，逐条抄：

- 黑板全样本聚合口径 `REAL_GRADES_PER_PT = 2.61`（137 匹练成马娘 24,114 grade / 9,240 pt）；
- 本剧本可核的那一局（card 114101，t78 五维 2244/1750/1845/1349/1296、PT 8,450、官方 `rank_score` 72,142）
  反推只有 `18,297 / 8,450 = 2.17`；
- 直接量到的 Σgrade 19,492 给 `2.31`；
- **取中间值 2.35，使 72,142 的残差落在 1% 内**。
- 注释自己标注：⚠「**这个数是拟合出来的，不是量出来的机制**（2026-10-31 标注）……不要拿它当门禁」。

还有第二个没定的分叉：**2.35 该除「总得到 PT」还是「实付 PT」**。本机收的一局（PT 8,339 / 实付 7,649 / Σgrade 17,022）
按总 PT 是 2.04、按实付是 2.23，**两个都不到 2.35**。

⇒ 结论：2.35 是一个**为对齐 72,142 这一个锚点而定的标量**。它的合法使用范围就是 72,142 附近，
外推到 91,400（+27%）没有依据。

## 3. 拿 LF 卡做交叉验证（2026-11-02 新证据）

分数线表本地有两份独立一手数据，**逐档一致**（148 档到 105,399 完全相同，只在 LE 以上插件把 LE..LS24 合并成「LE以上」）：
`E:/HJM/umaai_next/gamedata/constants.json`（`rank_names`/`rank_scores`，298 档，末档 LS24=190,400）
与 `E:/HJM/_ref01/matsuri-ref-01/data/rank_table.json`（源 URA-Plugins `GradeRank.cs`）。
**LF 起线 = 91,400；LF4 = 93,800–94,399；LF5 = 94,400。**

真机 LF 卡（截图，2291/1857/1804/1706/1848，五维和 9,506，评分 94,372 → 正好落 LF4）代入 `real_score`：

| 步 | 值 |
|---|---|
| 五维分 `Σ table(revise(五维))` | 63,626（revise 后 3382/2514/2408/2212/2496） |
| 残差 = 94,372 − 63,626 | **30,746** |
| 反推 `skill_pt` = 30,746 ÷ (1.0746×2.35) | **≈ 12,176 PT** |

对照：我们锚点那局真机 PT 是 8,449。**两种可能，现在分不开**：
1. LF 卡真有 ~12k PT ⇒ 2.35 这套折算在 LF 段仍然成立；
2. LF 卡 PT 只有 ~8.5k ⇒ 五维分只能给 63,626 + 21,336（= 1.0746×round(8449×2.35)）= 84,962，**缺 9,410 就是没建模的「真技能分」**。

`skill_data.grade_value` 逐技能只有几百（白 85–508 / rarity5 340），十几张技能凑不出几万 ⇒
真技能分的构成**仍是黑的**，不能拿它排除可能 2。

## 4. 这个系数对「能不能凹到 LF」的影响（实测）

`matsuri-dist` 历史锚点扫描（`out/_dist_anchor_t*_s*.json`，n=2000/格；s1.0 与 s1.6 只差注入锚点五维，**PT 完全相同**）：

| 出发回合 | 五维和均 | real 均 | P(≥LF) |
|---|---|---|---|
| t15 | 6,612 / 7,211 | 44.5k / 51.7k | 0.00% |
| t20 | 7,795 / 8,423 | 62.9k / 71.6k | 0.20% / 1.10% |
| t30 | 7,822 / 8,380 | 62.9k / 70.7k | 0.90% / 6.70% |
| t37 | 8,769 / **9,312** | 77.5k / **85.6k** | 13.75% / **33.50%** |
| t45 | 9,146 / **9,468** | 82.9k / **88.0k** | 12.55% / 28.55% |
| t60 | 8,692 / 8,838 | 71.9k / 74.0k | 0.05% / 0.45% |

三条要记的：

1. **同一批采样换引擎原生 `score` 口径，P(≥US7) 全为 0%**（US7=71,600）。两套口径差 ~1.4 万 ⇒
   档位结论完全由口径决定，不由局面决定。
2. `real_score` 对五维和的敏感度 **≈ 15 评分 / 五维点**（+543 五维和 ⇒ +8,121 评分；
   >1200 段 `revise` 翻倍再乘表尾斜率 ~7）。所以冲 LF 的杠杆是**五维和站上 9,300**，不是 PT。
3. P(≥LF) 从 0.9% 到 33.5% 只靠「把注入锚点五维乘 1.6」得到 ⇒ 这个百分数是**假设局的相对趋势**，
   不是我们常规产出的达成率。真机 t78 那份 state（整局已打完，4000 次只在收尾抖）
   real 均 63,032 = UA9–US 档，P(≥LF) = 0%。

## 5. 铁律落点

- **门禁不看评分 / 档位 / P(≥LF)**。门禁只认 `gate` 里的三分量 `five_sum` / `stat_score` / `pt`
  （`dist.rs:178-185`，三项都不含拟合系数），CRN 同种子逐局配对的贴近幅度 95% 区间。
- `real_score` 只允许用于**面板显示**，且必须带「含 2.35 拟合系数、为对齐 72,142 而定」的标注。
- 禁止为了让某个档位达标去调 `MC_GRADE_PER_PT`（该环境变量可覆盖 2.35，`dist.rs:57`）——
  那就是用系数凑分。

## 6. 裁决需要什么（可执行）

1. **LF 卡的「育成情報」页**：拿它的真实总 PT / 实付 PT。有这一个数就能在 §3 的可能 1 / 可能 2 之间分开，
   顺带裁决 2.35 该除哪个 PT。
2. **同一局同时读** 评分 + 五维显示值 + Σgrade（从游戏技能清单直接数，不用折算）——
   这是把「计分用原始值 vs 显示值」钉死的唯一办法。
3. 真机报文里 `chara_info` 的评分字段口径（已有 5,591 个报文在 `E:/HJM/jidianbeiAI0.22/out/hachimi_raw`）。

拿到 1 之后再做的事：把 `real_score` 的技能项换成**逐技能 Σ 真值**（`skill_data.grade_value` 的构成需要先量明白），
然后 `MC_GRADE_PER_PT` 这个开关就可以删了。
