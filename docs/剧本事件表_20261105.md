## 2 三条口径纪律（第一遍踩过，写死）

1. **身份键 = `(event_id, story_id)`，不是 `event_id`**。39 个 `event_id` 挂着多个 `story_id`
   （`10002`×50、`10000`×24、`20000`×18、`10012`×9…），只按 id 聚合会把不同事件并成一个。
2. **`event_id` 不是稳定外键，唯一稳的 join 键是 `story_id`**。
   420 个身份对里按 `single_mode_story_data.id` 能连上的只有 **59 个**：45 个在 400015 族、
   14 个在 400000 族（命中的都是 `215022`/`215806` 这种 5–6 位 id）：

   | 族 | id join 命中 / 该族对数 |
   |---|---|
   | 剧本15自持（400015…） | **45 / 45** |
   | 剧本级其他（400000…） | 14 / 24 |
   | 角色事件（5010…/5011…） | **0 / 263** |
   | 卡·支援事件（80…/82…/83…） | **0 / 88** |

   连不上的正是**低位 id** 那批：`7040/7041`（story `400000040`，按 id 查会得到
   `501072704/501072705`、`card_chara_id 1072`）、`1011`（story `400000035`，按 id 查得
   `501018522/1018`）、以及 `10, 1000, 1001, 1007, 1012, 3001, 7005, 7031, 7032`。
   #37 在 `7040` 上踩过一次（`docs/继承事件一手_20261103.md:31-34`），本文把它量化成

3. **效果只在「同一面板回合的相邻跳」且本跳响应不带赛事/选项奖励**（`PS.POLLUTE` =

## 4 结构是链，不是表

「消费 X 的同一跳新入队 Y」的前几对（全量在报告 §6）：

```
7005 -> 215022 ×51     215022 -> 10002 ×46     7003 -> 215022 ×35     215043 -> 21263 ×29
7005 -> 7003 ×27       20099 -> 21263 ×24      1011 -> 215022 ×23     215022 -> 10000 ×18
7044 -> 7040 ×10       7040 -> 7045 ×10        215001 -> 215042 ×11   215042 -> 215073 ×11
```

⇒ 一个事件结算会**产出**后继事件；想按「回合 → 事件」建平表会漏掉这层依赖。
`7044 → 7040 → 7045` 正是 #54/#37 的继承腿：7040 夹在两个角色事件之间，每局一次、在面板 t31。

## 8 裁决

1. **不接线、不写 `data/`、不动 `no_event_turns`**：本文只把「有没有事件、哪个事件、哪一跳结算、
   带不带选项、变了哪些状态」定住；收益侧的 Δ 均值是**观测**，不是可当常数的公式（铁律）。
2. **可复用的观测器**已成型：`hops()` 给出 (run, 跳, 事件身份, Δ, 是否干净, 链后继)，
   任何「某事件到底哪天生效、生效了些什么」的后续问题直接用这只口子，不必再写解码。
3. **下一步该问的不是 `no_event_turns`**，而是：80.2% 无选项的结算要不要进引擎（它们不改状态，
   大概率不进）；44.4% 有 Δ 的结算里，**每局恰好一次且带选项**的那一小撮才是决策层缺的东西
   —— 这需要先按族拆出候选集，再做配对 CRN 才谈接线。
4. **样本限制**：13 局里只有 10 局跑到 t55 之后、覆盖到 t78 的更少；族内按局的极差没做检验。
   加样路径 = 继续打真机到结局，本表的「每局恰好一次」子集会自然收紧。
