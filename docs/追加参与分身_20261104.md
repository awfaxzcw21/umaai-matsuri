# 追加参与（`sub_command_partner_array`）＝分身：一手读数与缺口定位 2026-11-04

任务号 #46（= #40 第 2 条）。结论先说：**这块机制在文档里已经定过语义（`docs/matsuri_memo_cn.md` §3.5 分身），
引擎里一行实现都没有**（`grep -riE "分身|sub_command|extra_partner" crates/` 零命中），
而且它**按时点门控**出现——这解释了为什么我们一直没看见它。本文只登记读数与缺口，**不接线、不写 `data/`、不造常数**。

## 1. 口径先钉死

抽取脚本 `tools/train_leg_preview.py:79-88`：

- `heads_deck` = 站在这条训练命令上的**卡组支援卡**数；
- `heads_sub`（`nsub`）= 其中**同时出现在 `sub_command_partner_array`** 的那些 ⇒ **`heads_sub ⊆ heads_deck`**；
- `heads_own = heads_deck − heads_sub` = 真正的「站位排布」口径（与引擎可比的那一份）；
- `heads_other` = 编组外 NPC；`heads_total = heads_deck + heads_other`。

⇒ 引擎的站位模型对齐的是 `heads_own`，`heads_sub` 那一块在引擎里恒为 0（**这是机制缺失，不是策略差异**）。

## 2. 出现率：按命令类型

数据 `out/train_leg_preview_20261103.csv`（13 局、4,990 条候选命令、760 块板），keep 口径同 `tools/train_leg_gap_split.py::real_board()`。

| kind / camp | 候选条目 | 有追加的比例 | 追加/条目 |
|---|---|---|---|
| 稽古 keiko，非合宿板 | 1,460 | 27.6% | 0.321 |
| 稽古 keiko，合宿板 | 580 | 23.4% | 0.262 |
| 普通训练 plain，非合宿板 | 2,950 | 3.4% | 0.040 |

条件化（只看候选条目，未做落子选择）：

- `heads_deck = 0 ⇒ P(追加) = 0`（稽古/普通都严格为 0）⇒ **追加只发生在已有人头的命令上**，不是「凭空铺一格」。
- 稽古里 P(追加) 随 `heads_deck` 单调上升：0 / 10.7% / 37.6% / 56.6% / 67.9%（deck=0…4），追加/条目 到 deck=4 时 1.179。
- 稽古里 `tips = 0 ⇒ P(追加) = 0`（1,766 条 tips>0 的才有）；但全样本里有 40 条 `tips=0 且 heads_sub>0` ⇒ **tips 不是硬前提，只是稽古层的强相关**。
- 板内结构：760 块板里 285 块有追加，**有追加的槽位数可以是 5（50 块板五个槽全带追加）**，板内追加总数最高 7。
  ⇒ 这不是「教诲 +1 人」的单点事件，而是**同一名担当同时坐在多个训练位**（分身）才会出现的形状；
  板内 Σ`heads_deck` 最高到 13，而卡组只有 ~5–6 张卡 ⇒ 只能是重复计数。

## 3. 决定性的一条：按时点是 0 → 42% 的开关

| 回合段 | 候选条目 | P(追加) | 追加/条目 |
|---|---|---|---|
| t1–13 | 713 | **0.0%** | 0.000 |

| t40–52 | 905 | 8.2% | 0.091 |
| t53–65 | 892 | 22.3% | 0.262 |
| t66–78 | 796 | **42.3%** | 0.491 |

`有追加板` 与 `无追加板` 的平均回合都是 18.0（板数按回合均匀铺开），所以这不是「后期板本来就少」的抽样假象。

**分层后时点仍在**（这是关键一步：Lv 与 tips 也随时点涨，必须把它们固定住才敢说是时点门控）。
固定 `kind=keiko`、`level=2`、`tips>0`，只变回合段：

| 回合段 | n（条目） | P(追加) |
|---|---|---|
| t14–26 | 49 | **0.0%** |
| t27–39 | 289 | 10.4% |
| t40–52 | 290 | 14.1% |
| t53–65 | 384 | 39.1% |
| t66–78 | 455 | **69.9%** |

再叠一层 `heads_own ≥ 1`（排除「无人头命令本来就不能有追加」的机械效应）：0.0% / 8.8% / 11.1% / 34.5% / 65.3%
——**同向、同量级**。⇒ 时点效应不是 Lv 或 tips 的影子。

另一侧的合取条件同样硬：`kind=keiko, level=2, tips=0` 在**全部四个后段**（t27–78，n=201）里 P(追加)= 0。
`tips` 列 = `len(tips_event_partner_array)`（`tools/train_leg_preview.py:87`，脚本里把它标成「教诲人数」，
与「叹号/灵感参与者」的语义在本仓还没敲死 ⇒ 登记为待核，不许当已证前提）。

这与 §3.5 记录的**分身来源**是同一个形状：分身只在「身上有 +1 人来源」时出现——
URA 期全演目带 +1、已授的协助教诲、合宿中的牵绊（`matsuri_memo_cn.md:386`、`:524`）。
URA 期在末段 ⇒ 前半程 0 完全说得通。

**未被本文证明的部分（必须留着）**：

- 来源归属（到底是 URA、协助教诲，还是牵绊）无法从现有 CSV 分辨——CSV 只有计数，没有 partner id。
  需要回报文把 `sub_command_partner_array` 的**具体卡 id** 抽出来，与「该卡的教诲/牵绊状态」对表。
- **合宿反而更低**（23.4% vs 非合宿 27.6%）与「牵绊＝合宿中额外 1 人」不吻合。
  ⇒ 不许把「合宿 +1」当成已证机制写进任何实现。
- 有追加的板整体更肥（平均 Lv 2.14 vs 1.52、tips 率 0.60 vs 0.30、Σ人头/槽 1.28 vs 0.75）——
  这一层混淆已用上面的固定 (Lv, tips) 分层剥掉；**剩下的混淆是「来源数本身也随时点长」**
  （URA 期开、教诲陆续授予），本文分辨不了「时点」与「来源累积」，两者都要 partner id 级数据才拆开。

## 4. 这块缺口落在哪条腿上（为什么值得做）

#40 的三项分解里，稽古 home 腿的 −427 Pt/局 几乎全在「落位/手数」项，而其中最大一桶是**人头 = 3**：

| 人头桶 | 真机手/局 | 引擎手/局 | 落位效应（Pt） |
|---|---|---|---|
| 2 | 10.50 | 7.87 | −121.5 |
| **3** | **8.83** | **0.12** | **−596.8** |
| 4 | 0.50 | 0.00 | −43.3 |

引擎在 heads=3 这一桶几乎从不落子（0.12 手/局），真机落了 8.83 手/局。
`heads_sub` 正是把命令从 2 人抬到 3 人的那一份——**没有分身机制，引擎的盘面永远凑不出真机那种 3 人稽古**。

同一份账也解释了 #41 的 owner 重算：换强策档后「追加参与」那块仍是恒 1.169（策略档不动它），
它的对数份额因此从 19% 升到 **22%**，而站位那块完全不随策略档变。
