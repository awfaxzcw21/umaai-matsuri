## 4 这批样本能用来做什么、不能做什么

**能**：
- 当**输入规格**用——#77（报文→引擎整局输入）可以按这张表搭一套「LG15 组形状」的
  卡组＋双亲喂进引擎，量引擎在同一输入下产出多少；这比继续用 `_state_t30.json`
  （cap 6／R 吾妻／写死蓝因子）有意义得多。
- 当**两腿目标**用——五维和 9,345／总PT 10,250 是硬指标，比「分数要到 85,600」可分解。

**不能**：
- **没有逐回合轨迹**。这些是终局快照，不能和引擎局做回合级对账（同 #55 §1 那句限制：
  落点在 `.trained_chara[]`／继承事件侧，拿不到每一手）。
- **组间不等于因果**。凸数/卡位与分数的关系是「高分组都这样」，不是「改成就涨 X 分」。
  要因果只能靠配对 CRN（#77 那条路）。
- 档位线（85,600=band114、91,400=band124）来自 `master.mdb single_mode_rank`，
  见 `docs/评分档位分数线表` 那条记忆；本文不重述。

## 5 顺带钉住的三条小事实（一手，值得单独记）

1. **`support_card_list` 的键**是 `position / support_card_id / exp / limit_break_count /
   rental_type / friend_type / is_rental`——**不是** `card_id / rarity`。
   面板 `history.jsonl` 那边写的是 `card_id / limit_break`，两套命名别混用。
2. **`total_skill_pt` 是累计获得 PT**（样例 10,961），与 #55 里「LF 卡 PT 10,961」同值同源，
   不是余额。余额在 `skill_point`。
3. 用户自己名下在这批采集面里**只有一匹 ≥85,600**：`111602 tc607`，**87,387 分但 scenario_id=14**。
   ⇒ 剧本15 线内账号可核最高仍是 #55 定的 **72,898**，本文不改那个数。
