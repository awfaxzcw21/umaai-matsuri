# #78 人头定价改判：引擎不是「没给人头定价」，是**闪彩人头超价 + 闪彩人头拿不到**

日期 2026-11-06（03:05）。产出：`tools/shining_head_packet.py`（只读报文，复用 #40 的解码件）
＋壳 `_wt_head`（分支 `fix/head-slope`）内单测 `forced_shining_head_pt_must_not_exceed_packet_median`。
没动 `data/`、没动引擎生产代码、没操作游戏。

## 0 一句话

#41 判「缺口在估值没给人头定价」，#42 用 `HEAD_BOOST` 排序键把 PT 买到 +669——两条都建立在
**按「卡组人头数」分桶**的对照上。把同一个桶换成**按「闪彩人头数」分桶**（`b80` ＝
`training_partner_array` 里 <100 且 `chara_info.evaluation_info_array` 给的评价 ≥80 的个数，

| 闪彩人头 b80 | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| 真机 PT 中位（Lv2-4 合并） | **8.0** | **16～17** | **28～30** | **42～46** |
| 引擎（强制全闪彩，壳内单测 Lv2） | **7** | **17** | **43** | **117** |
| 每人头倍率 | — | 真机 **1.76～1.94** | | 引擎 **2.55** |

⇒ 引擎对**可闪彩的人头**给价**比真机陡 ~35%**（2 头时 43 vs 29.5＝1.46×；3 头时 117 vs 42＝2.6×）。
⇒ 所以整局 PT 低（cap-10 锚点上 −12.1%）**不是公式欠**，而是**引擎盘面上拿不到闪彩人头**：
真机落子格 2.34 人头、引擎只落 1.03，而引擎的估值明明更爱闪彩人头——它不追，说明

判据（下一步用，先写死）：同一块板上分别用「即时 PT」和「终局值」对五格排序，

## 5 第四条探针（03:45）：软上限对 PT 根本不成立，形状才是关键

三句结论：

1. **§4 的主嫌疑对 PT 不成立**：PT 全程 **7 → 117 不动**，`soft_cap_gain`/`cap_decay_factor`
   一点没砍到它（只砍五维：173→86）。所以「终局值因软上限而放弃人头格」这条**解释不了 PT 腿**。
2. **真正的差异是形状**：真机 b80 0→3 ＝ 8 / 16 / 29 / 42（差分 +8/+13/+13 ⇒ **近似线性，+13/头**），
   引擎 ＝ 7 / 17 / 43 / 117（倍率 2.4/2.5/2.7 ⇒ **几何，×2.55/头**）。
   **1 头时两边几乎相等（16 vs 17）**，从第 2 头起分道——所以问题不是「人头单价错」，
   是**多张卡的贡献在引擎里连乘、在真机里近似相加**。
3. ⚠ **本探针的边界（04:30 已用报文核掉一半）**：原先担心「把 3 张卡全设成 `friendship=100`」是上界，
   因为真机羁绊可能是 80～100 的分布。**这条保留被数据否掉了**：回合≥30 的普通训练条目里，
   闪彩人头的羁绊 **2,918/2,942 ＝ 99.2% 就是 100**（p25/med/p75 全 100，min 86），
   而全部卡组人头里羁绊 <80 的只占 **0.3%**（9 个人头在 74）。
   ⇒ 羁绊这一维不用改，`friendship=100` 就是真机常态。
   **剩下的唯一边界是类型匹配**：真机 3 人头格中「3 张全闪彩」占 56/(56+3+4+28) ＝ 62%，
   而这 56 条的 PT 中位就是 **42～46**——探针里同为 3 闪彩人头的引擎给 **117**，
   ⇒ **2.6～2.8× 的超价是实的，不是配置假象**。

**下一步（唯一动作，判据先写死）**：把探针里的 `friendship=100` 换成**报文实测的羁绊分布**
（`chara_info.evaluation_info_array` 的取值直方图，一手可取），重跑同一张表。
- 若换成真实羁绊分布后引擎落到 ≈8/16/29/42 ⇒ **公式没问题**，#78 到此结案，PT 腿回去找别的来源。

  那时才谈得上改公式，且必须配一条「3 头 PT ≤ 真机上界 42×1.3」的单测锁住。

不许做的事：给人头乘子拍一个新常数、或把 ×2.55 直接改成 ×1.85——那是拟合，不是机制。

## 8 B 条机制落到一行代码（05:15）

`umaai_next/crates/umasim/src/game/support_card.rs:43-47`（**上游，只读**）：

```rust
pub fn add(&self, other: &CardTrainingEffect) -> Self {
    Self {
        youqing: (100.0 + self.youqing) * (100.0 + other.youqing) / 100.0 - 100.0,
        ganjing: self.ganjing + other.ganjing,
        xunlian: self.xunlian + other.xunlian,
        ...
```

**友情在卡与卡之间连乘，干劲/训练効果相加。** 单卡友情 35 时：1 张 35 → 2 张 **82.25** → 3 张 **146**，
与 §6 实测的 35 / 82 / 155 逐位对上 ⇒ §6 那条「友情合计超线性」不是固有效果门控，
**就是这一行的连乘结构**。真机侧同位置是相加带（实测 3.27× vs 相加预测 2.96× vs 连乘 3.96×）。

**但这一行不是全部**：把友情改成相加（2 张＝70）后，引擎 2 人头倍率按 §6 的乘区只能从 6.75× 降到
约 6.3×，仍远高于真机 3.27× ⇒ **还有第二个连乘源没定位**。候选（都要一手判据，不许猜）：
1. `training_leg` 里教诲 `advice_mods_train` 的主/副获得量乘区是否按人头数重复计入；
2. `shining_count(train) > 0` 门控的 `unique_effect_type=13`（`support_card.rs:228`）
   与 `type=20`（巨匠，按卡组种类数给副属性词条）在同一格被多次点亮；
3. 発表会/彩圈 `friend_mult` 与 `(1+0.05·人头数)` 之外的隐藏乘子。

**§8 这条定位方法已作废（05:25 报文核实）**：`params_inc_dec_info_array` 每行只有一个
`target_type` + 最终 `value`（样例 turn67／cid103／2 闪彩人头：`1=2, 3=4, 4=32, 30=25, 10=-23`），
**没有逐乘区的分解行** ⇒ 拿报文对「友情 vs 訓練効果 vs 固有」这条路走不通，上面 1/2/3 不能这么裁。

**修的顺序因此反过来：先 A 后 B。** 理由是可识别性，不是量级：
A（单卡倍率 2.62 vs 一手 1.98）**不涉及任何聚合方式**，1 人头时 `add()` 根本没被调用第二次，
所以它是干净可判的单变量；B（聚合方式）只有在 A 修对之后才谈得上量——现在引擎 m2 里
A 的 32% 偏差和 B 的连乘是乘在一起的，先动 B 会把两个错混成一个更大的未知。

A 的下一步（可离线做完）：拿 cardDB 里这几张卡的 `友情/訓練効果` 原值，

**但先别改——有一条反证未解**：五维走的是同一个 `friend_mult`（`mod.rs:640-644` 的 `with_friend`），

   受影响的只有 PT 一行，改 `pt:` 那一行即可，五维不动。

**判据（下一步，先测再改）**：同一块板上分别取「锚点在场（注入态）」与「无锚点（离线表算）」两臂，
